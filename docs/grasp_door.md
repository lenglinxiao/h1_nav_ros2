H1-2 "抓握后拉"手势开发文档
    日期：2026-11-19。本文自包含：外网开发时不需要访问内网仓库，所需的模型参数和计算结果都在文中。
    开发仓库：GitHub lenglinxiao/h1_nav_ros2。下文路径都相对这个仓库的根目录（ROS2 工作区根目录）。
    标"待验证"的内容还没在真机上确认；标"初值"的数字要上车标定。
    1. 目标
        H1-2 人形机器人站在车门旁，用右手做"抓握后拉"手势，触发问界 M9/M8 的隔空开门：
            1. 手靠近车门把手，掌心朝门；
            2. 握拳；
            3. 往回拉 10–15 cm；
            4. 车门自动打开。
        车端前提：P 挡、车辆已解锁（钥匙在附近）、车机启动、主驾无人，并且在"设置 > 车辆控制 > 体感控制"里打开手势开关。识别靠车侧摄像头，所以手要完整落在摄像头视野里，动作不能太快。
        路线：不训练，不做 mimic。
        腿：交给宇树原厂运控，由它站稳；
        右臂：用 arm_sdk 按写死的关键帧播放；
        Dex5 灵巧手：只在"张开"和"握拳"两个手型之间切换。
        最终交付形态：在导航 Web 界面和桌面界面的"到达后动作"里多一个"抓握后拉"。机器人导航到车门旁的停靠点后自动执行，执行完再继续后面的路线。
        为什么选这条路：
        动作很简单：腿不动，只有一只手臂走几个姿势，用不上全身动作跟踪。
        位置和节奏要能精确调：手停在哪、拉多远、拉多快，都要按车的识别要求调。用关键帧，改几个数就行；用 mimic，每改一次都要重录、重训。
        平衡不依赖自训策略，避开了 sim2real 风险。
        能直接接进导航现有的手势链路（wave_hand、reach_hand 就是这么接的）。
    2. 原理
        2.1 原厂运控和 arm_sdk
            机器人站立后，原厂运控一直在机器人内部运行，负责全身电机，并根据 IMU 和关节状态实时做平衡。
            它监听 DDS 话题 rt/arm_sdk。外部程序往这个话题发 LowCmd_ 消息，里面有腰和双臂共 15 个关节的目标，再加一个权重 w（放在 27 号位的 q 字段）。
            运控对上肢每个关节，按下面的公式混合自己算的目标和外部发来的目标：
                \[ q{最终} = q{运控} \times (1-w) + q{arm\sdk} \times w \]
            腿不受影响，始终由运控控制。
            所以"伸手"的本质是：程序每 20 ms 告诉运控"右臂这一刻应该在哪"，这些角度沿一条平滑曲线逐帧变化，手臂就被一点点带到目标姿势。程序不碰腿，也不直接驱动电机。
            一次完整手势分三段：
            1. 接管：持续发"当前姿势"，同时把权重从 0 慢慢升到 1。发的就是手臂当前的位置，所以手臂不动，只是控制权换手；
            2. 播放：权重保持 1，逐帧发关键帧之间的插值；
            3. 交还：保持最后的姿势，把权重慢慢降回 0。
        2.2 为什么不用训练
            伸手确实会扰动平衡，但扰动很小。按模型算（见 5.4 节），右臂从自然下垂伸到水平前伸，整机重心前移约 2.6 cm，大约是脚长（25 cm）的十分之一。原厂运控的平衡是闭环控制，自己就能扛住这种扰动；原厂自带的握手动作 ShakeHand(0) 也是手臂前伸、腿保持站立。
            "要不要训练"取决于有没有把原厂运控换掉，而不是手臂动不动。只有在进调试模式、全身走 rt/lowcmd 的时候，平衡才需要我们自己训练出来，那是第 10 节的备用路线。
            可能出问题的情况：动作太快（惯性力变大）、手上有接触力（隔空开门不碰车，所以没有）、边走边伸手（方案里会先停下来再做手势）。
        2.3 电机怎么跟踪目标
            每个电机执行 PD 控制加前馈：
            \[ \tau = kp (q^ - q) + kd (\dot q^ - \dot q) + \tau_{ff} \]
                反馈用的是此刻编码器测到的 \(q\)、\(\dot q\)，第一帧就有，不需要历史数据。
                前馈 \(\tau_{ff}\) 不看测量值，用来事先抵掉已知的力，比如重力。
                反馈回路运行在电机驱动和运控那一层，频率远高于 50 Hz。我们的程序只负责每 20 ms 给出一个新的目标角，是"出题的"，不是"纠错的"。
                前馈填 0 时，重力会让关节留下稳态误差。粗估右肘约 7°，换算到手掌约 4 cm，见 5.5 节。

    4. 接口要点
        4.1 arm_sdk
            以 unitree_sdk2/example/h1/high_level/h1_2_arm_sdk_dds_example.cpp 为准。
            | 项目 | 值 |
            | --- | --- |
            | 指令话题 | rt/arm_sdk，类型 unitree_hg::msg::dds_::LowCmd_ |
            | 状态话题 | rt/lowstate，类型 unitree_hg::msg::dds_::LowState_ |
            | 电机索引 | 12 腰（waist yaw）；13–19 左臂；20–26 右臂 |
            | 权重 | 索引 27（kNotUsedJoint）的 q，取值 0–1 |
            | 每个关节要填的字段 | q、dq、kp、kd、tau |
            | 例程增益 | 双臂 kp 为 120/120/80/50/50/50/50，kd 为 2.0/2.0/1.5/1.0/1.0/1.0/1.0；腰 kp 200、kd 2.0 |
            | 例程周期和限速 | 20 ms，0.5 rad/s |
            单臂关节顺序：肩 pitch、肩 roll、肩 yaw、肘、腕 roll、腕 pitch、腕 yaw。
            要点：
                只能在原厂运控运行时用，进调试模式就失效；也不能和走 rt/lowcmd 的自训策略 h1_2_policy_bridge 同时运行。
                权重对腰和双臂同时生效。只动右臂时，腰和左臂也必须每帧都发"保持接管时的角度"，否则会被拉走，或者因为 kp 为 0 而软掉。
                先读状态再动。接管前要确认收到了 rt/lowstate；如果读到的角度全是 0 就往外发，手臂会跳。
                宇树中文文档里的上肢控制页面讲的是初代 H1（4 自由度手臂，权重在索引 9），不要照那个页面写。
            官方例程里有三个坑：
            1. 开头直接把权重设成 1，同时把关节目标从当前角度插值到初始姿势。因为第一帧的目标就是当前角度，所以不会跳。我们的方案改成"先保持当前姿势、再慢慢把权重升上去"，更保守。
            2. 结尾的权重没有降到 0：weight_rate = 0.2、stop_time = 2 s，一共只减了 0.4，退出时权重还停在 0.6。拿它验证"权重归零时平滑交还"之前，要先把交还时间加长到 5 s，或者把降权速率改成 0.5。
            3. 读状态之前不检查是否真的收到过 rt/lowstate。
        4.2 LowState_ 常用字段
            | 字段 | 含义 | 单位 |
            | --- | --- | --- |
            | motor_state()[i].q() / .dq() | 第 i 个电机的实际角度 / 角速度 | rad / rad·s⁻¹ |
            | motor_state()[i].tau_est() | 估计力矩 | N·m |
            | imu_state().quaternion() | 机身姿态四元数 (w, x, y, z) | — |
            | imu_state().gyroscope() | 机身角速度 | rad/s |
            | imu_state().rpy() | 机身横滚、俯仰、偏航角 | rad |
            | tick() | 帧计数 | — |
            | mode_machine() | 机型编号，现有 bridge 按 6 校验 H1-2 | — |
            motor_state 和 LowCmd_ 的 motor_cmd 下标一一对应；同名的 q，在状态里表示"实际在哪"，在指令里表示"希望到哪"。发布频率没查到官方数字，宇树给 G1 写的是 500 Hz，H1-2 以实测为准。

        4.4 现有手势链路（仓库内）
            UDP 协议
            h1_2_loco_udp_daemon 只监听 127.0.0.1:39001，每条指令是一行文本：
            | 指令 | 回复 |
            | --- | --- |
            | gesture &lt;name&gt; | ok &lt;ret&gt; &lt;message&gt; 或 error &lt;ret&gt; &lt;message&gt; |
            | stop | 有回复 |
            | vel &lt;vx&gt; &lt;vy&gt; &lt;wz&gt; [duration] | 只在出错时回复 |
            ROS 服务
            /h1_2_loco/execute_gesture，类型 h1_2_nav_msgs/srv/ExecuteGesture：
                请求：string name；
                返回：bool success、int32 sdk_ret、string message。
            转发节点 gesture_to_h1_2_loco 把 name 拼成 gesture <name> 通过 UDP 发出去，然后最多等 20 s 回复。只有回复是 ok 且返回码为 0 时，才判定成功。
            守护进程现状（src/h1_2_loco_bridge/src/h1_2_loco_udp_daemon.cpp）
            主循环是单线程的，recvfrom 超时 200 ms；
            启动时初始化一次 DDS；
            超过 --command-timeout（默认 1 s）没收到 vel，就自动 StopMove() 一次；
            原厂手势都是先 StopMove()，再调 LocoClient，SDK 调用返回后立即回复；
            已经链接了 unitree_sdk2，编译用 C++20。
            路线执行器（src/h1_2_nav_tools/h1_2_nav_tools/teaching_route_runner.py）
            把收到服务回复当作"手势做完了"，回复以后马上继续走下一段路线。

            | 关节 | 下限 (rad) | 上限 (rad) |
            | --- | --- | --- |
            | 肩 pitch | −3.14 | 1.57 |
            | 肩 roll | −3.4 | 0.38 |
            | 肩 yaw | −3.01 | 2.66 |
            | 肘 | −0.95 | 3.18 |
            | 腕 roll | −2.75 | 3.01 |
            | 腕 pitch | −0.4625 | 0.4625 |
            | 腕 yaw | −1.27 | 1.27 |
            腕 pitch 的范围很窄，调掌心朝向时主要靠腕 roll 和肩 yaw。
        5.2 关节方向（正运动学核对过）
            肩 pitch：越负，手臂往前抬得越高。0.28 左右是自然下垂。
            肘：0 时已经弯成 90°，正值往伸直方向，负值弯得更多。
            肩 roll：对右臂来说越负，手越往外张。
        5.3 候选姿势和手掌位置
            坐标系是骨盆坐标系：x 向前、y 向左、z 向上，单位 m。手掌点用的是模型里的 right_palm 位置，没装 Dex5。仿真里骨盆离地约 1.0 m。

            | --- | --- | --- | --- |
            | 自然下垂 | 0.28, 0, 0, 0.52, 0, 0, 0 | (0.13, −0.22, −0.11) | 斜向下 |
            | 胸前 | −0.20, −0.23, 0.90, −0.55, 0, 0, 0 | (0.20, −0.03, 0.25) | — |
            | 前伸偏低 | −0.8, −0.15, 0, 1.2, 0, 0, 0 | (0.52, −0.23, 0.08) | 前下方 |
            | <b>前伸水平</b> | <b>−1.0, −0.15, 0, 1.0, 0, 0, 0</b> | <b>(0.59, −0.19, 0.24)</b> | <b>水平向前</b> |
            | 前伸偏高 | −1.4, −0.15, 0, 1.5, 0, 0, 0 | (0.63, −0.16, 0.33) | 前方略向下 |
            在胸前姿势下，Dex5 的碰撞体离躯干只有约 1.5 cm，真机上先确认不会蹭到身体。要算别的姿势，可以用附录 A 的连杆参数自己做正运动学。
        5.4 平衡扰动
            | 项目 | 数值 |
            | --- | --- |
            | 整机质量（含两只 Dex5） | 69.2 kg |
            | 右臂加 Dex5 的质量 | 7.3 kg |
            | 自然下垂 → 前伸水平时，右臂重心前移 | 0.24 m |
            | 整机重心前移 | 2.6 cm |
            | 绕踝关节新增的重力矩 | 17.4 N·m |
            | 脚掌范围（相对踝关节） | 后 0.08 m 到前 0.17 m |
            按 0.5 rad/s 慢速运动时，惯性力不到 1 N，主要的扰动就是重心的静态偏移。
        5.5 重力下垂（前馈为 0 时）
            前臂水平前伸时，肘关节以外的连杆加上 Dex5，重力矩约 6.3 N·m（把 Dex5 当作集中在手掌点上）。肘的 kp 是 50，稳态误差约 0.13 rad（约 7°），手掌大约下降 4 cm。
            这是粗估的上限，要在吊架上对比 rt/lowstate 和发出的指令实测。有三种处理办法：
                加重力前馈；
                适当提高 kp；
                示教时记录"发出去的指令值"，而不是实际测到的角度，否则回放时手臂还会再往下掉一次。
    6. 设计思路
        6.1 模块划分
            按"做什么 / 每一帧在哪 / 怎么发出去"分成三层，每层只管一件事：
            | 层 | 职责 | 改动频率 |
            | --- | --- | --- |
            | 动作描述 | 关键帧（胸前、到位、后拉）、每段用时、每段手型、增益、限速，全部放在配置文件里 | 最高：上车调参时改这一层，不用重新编译 |
            | 轨迹生成 | 把"从 A 到 B、用多久"变成每 20 ms 一个目标角；包括权重渐变、限速、限位裁剪 | 中等。这一层是纯计算，不依赖 DDS，单独做单元测试 |
            | 通信 | 读 rt/lowstate、发 rt/arm_sdk 和手型 | 最低：话题名和消息格式确定以后基本不动 |
            守护进程只负责调度：收指令、开始播放、中止、回复。它不关心轨迹怎么算。

        6.3 轨迹怎么生成
            关键帧之间用五次多项式插值
            \[ s(t) = 10t^3 - 15t^4 + 6t^5,\quad t\in[0,1] \]
            两端的速度和加速度都是 0，所以动作缓起缓停、不会顿一下。中点速度最快，是平均速度的 1.875 倍。
            限速的做法：拉长用时，不要截断
            每段的实际用时取：
            \[ T = \max\left(T{名义},\ \frac{1.875 \cdot \maxj |\Delta qj|}{v{max}}\right) \]
            这样曲线的峰值速度永远不会超过限速，每段结束时手臂正好到达目标，手型切换也和手臂到位对齐。
            官方例程的做法是"每帧最多走 0.01 rad"，这是截断。截断以后，手臂会落后于时间表：比如 1 秒内要走 0.9 rad，这一段结束时只走了 0.45 rad。后果是手还没到位就开始握拳，收回时也回不到起点。
            其他三项
                限位裁剪：目标角先按 5.1 节的范围裁剪，再插值。
                权重渐变：线性变化，接管 1 s（0 → 1），正常交还 2 s（1 → 0），中止时 1 s 内降到 0。
                频率：手臂指令和手型都每 20 ms 发一次。
            手型
            每段动作带一个手型（张开或握拳），这一段的每一帧都发这个手型。"握拳"那一段手臂保持不动，给手指留出握紧的时间。
            时长预算
            整套动作约 12 s（接管 1 s、动作约 9.5 s、交还 2 s），要保证在 ROS 侧 20 s 的超时以内。关键帧改了以后，总时长可能会变长，所以播放前先算一遍总时长，超过 18 s 就直接报错，不开始播放。
        6.4 怎么接进守护进程
            现有守护进程是单线程的，原厂手势调完 SDK 就立即回复。grab_pull 要连续发约 12 s 的指令，不能照这个模式做：
            | 问题 | 做法 |
            | --- | --- |
            | 放在主循环里执行，这 12 s 内收不到 stop | 在单独的工作线程里播放，主循环照常处理指令 |
            | 提前回复的话，路线执行器会以为做完了，机器人会伸着手臂开始走 | <b>动作做完才回复</b>：收到指令时先 StopMove()、记下请求方地址，由工作线程在结束时回复 |
            | 播放期间又收到一次手势 | 立即回复"忙" |
            | 播放期间收到 stop | 置中止标志，工作线程 1 s 内降权重、手张开，然后回复"已中止" |
            | 播放期间收到非零速度 | 拒绝，否则机器人会伸着手臂走起来 |
            | 进程被关闭（SIGINT/SIGTERM） | 先中止并等工作线程结束，再执行原有的收尾 |
            | 播放前没有最近的状态数据 | 不开始播放，直接回复错误 |
            | DDS 只能初始化一次 | 守护进程启动时已经初始化过，播放模块不再初始化；独立 demo 自己初始化 |
            建议新增的返回码（沿用现有"负数表示错误"的习惯）：
            | 返回码 | 含义 |
            | --- | --- |
            | −3 | 正在播放手势，忙 |
            | −4 | 被中止 |
            | −5 | 配置文件不合法 |
            | −6 | 没有收到机器人状态 |
            原有的 command_timeout 自动 StopMove() 可以保留，它只会让机器人停止行走，不影响手臂。
        6.5 配置文件里放什么
            每次触发手势时都重新读一遍配置文件。这样在车边改完参数，下次触发就生效，不用重启守护进程。
            | 类别 | 内容 |
            | --- | --- |
            | 时间 | 控制周期、接管时长、交还时长、中止时的交还时长 |
            | 限速 | 关节最大速度，初值 0.5 rad/s，挂吊架跑稳以后可以提到 1.0 |
            | 增益 | 双臂和腰的 kp/kd；右臂重力前馈，初值为 0，实测下垂后再填 |
            | 姿势 | 胸前、到位、后拉三组右臂角度；到位和后拉一开始和胸前一样，示教后再填 |
            | 手 | 话题名（待验证）、四指和拇指的增益、张开和握拳两组 20 个关节角 |
            | 动作序列 | 一串段落，每段写目标姿势（三组姿势之一，或者"起始姿势"）、名义用时、手型 |
            默认的动作序列：
            | 段 | 目标 | 名义用时 | 手型 |
            | --- | --- | --- | --- |
            | 抬到胸前 | 胸前 | 1.0 s | 张开 |
            | 伸到门把手前 | 到位 | 1.0 s | 张开 |
            | 停稳 | 到位 | 0.3 s | 张开 |
            | 握拳 | 到位 | 0.4 s | 握拳 |
            | 后拉 | 后拉 | 0.8 s | 握拳 |
            | 松手 | 后拉 | 0.2 s | 张开 |
            | 收回 | 起始姿势 | 1.5 s | 张开 |
            读取时要校验：数组长度对不对（右臂 7 个、手 20 个）、数值是否都是有限数、动作序列是否为空、引用的姿势是否存在、手型是否合法。校验不通过就不播放。
        6.6 测试思路
            单元测试只测纯计算部分，不需要机器人：
                1. 任意起点和终点，每帧每个关节的步长都不超过 \(v_{max} \cdot dt\)；
                2. 每段最后一帧的指令严格等于裁剪后的目标；
                3. 超出限位的目标会被裁剪到边界；
                4. 起点等于终点时，指令保持不变，帧数等于名义用时除以周期；
                5. 权重渐变的首帧和末帧取值正确；中止后 1 s 内权重降到 0；
                6. 配置不合法时（长度不对、出现 NaN、引用了不存在的姿势），返回错误。
            真机部分靠第 7 节每个阶段的验收标准来覆盖。

        | 事项 | 怎么验证或应对 |
        | --- | --- |
        | arm_sdk 在当前固件上是否可用 | 阶段 1 半天内就能知道；不可用就走第 10 节 |
        | arm_sdk 下我们发的 kp/kd 是否原样执行 | 吊架上改 kp，看下垂量是否跟着变 |
        | Dex5 指令话题名和关节顺序 | 阶段 2 订阅实际话题，逐个关节发小角度 |
        | 重力下垂 | 对比 rt/lowstate 和指令；用前馈或 kp 处理 |
        | 车不认机器人的手 | 训练解决不了；试戴肤色或白色的薄手套；找车端团队确认识别条件 |
        | 车门打开时扫到机器人 | 停靠点选在门的扫掠范围外，后拉结束后立刻收回 |
        | 防误触次数限制 | 每轮之间留间隔，并记录现象 |
        安全规范：
            首次上真机必须挂吊架；
            限速从 0.5 rad/s 起步；
            旁边始终留人拿遥控器，随时能切阻尼；
            不在调试模式下运行；
            不和 h1_2_policy_bridge 同时运行。
