# Preparation acceptance tools

The monitor subscribes to LowState and LowCmd. Build it against the same Unitree SDK and its CycloneDDS libraries as the policy node; for example, on the board with the existing dependency layout:

```bash
SDK=/home/unitree/h1_nav2_ros2_ws/third_party/h1_policy_runtime/unitree_sdk2
ARCH=$(uname -m)
g++ -std=c++17 -O2 -I"$SDK/include" -I"$SDK/thirdparty/include" -I"$SDK/thirdparty/include/ddscxx" tools/h1_2_policy_hardware/prepare_monitor.cpp "$SDK/lib/$ARCH/libunitree_sdk2.a" "$SDK/thirdparty/lib/$ARCH/libddscxx.so" "$SDK/thirdparty/lib/$ARCH/libddsc.so" -pthread -Wl,--disable-new-dtags,-rpath,"$SDK/thirdparty/lib/$ARCH" -o /tmp/h1_prepare_monitor
```

After review, install that binary at `/home/unitree/h1_nav2_ros2_ws/tools/hardware-preflight/h1_prepare_monitor`. The acceptance runner rejects monitor telemetry without schema 3 and `lifetime=until_stopped`, before authorizing output. The monitor runs until SIGINT or SIGTERM and has no 30-second lifetime limit; rebuild and install the new monitor before execution. `--fixstand-only` forbids the later services and requires a zero policy budget. `--fixstand-only` requires an explicitly selected finite positive `--fixstand-max-error` in radians. For full preparation the limit is optional: when omitted, error is recorded without a position gate; when supplied, an excessive error returns through Passive and revocation. The summary records whether the gate was applied. No threshold is recommended here. The default cumulative velocity limit remains 2 rad/s. For an explicitly reviewed continuous manual trial, `--walk-leg-speed-limit 3` uses 3 rad/s for SDK leg joints 0–11 only after the single pulse starts; upper-body joints remain at 2 rad/s and preparation stays at 2 rad/s. This requires the monitor's 27-element `peak_dq_by_joint` field. These are engineering trial thresholds, not manufacturer safety ratings. Dry-run is the default.

Execution also requires both `--confirm-debug-mode` and `--confirm-exclusive-control`. These flags are human assertions, not machine verification. Use them only after confirming the actual mode and exclusive control through the procedure applicable to the specific H1-2 and firmware; a keypress alone does not establish either condition. They default to false in dry-run.

Trace columns include q, dq, estimated torque and motor mode from the latest state and tau, mode, kp, kd, q and dq from the latest command, plus command mode_machine and mode_pr for each SDK index. They are asynchronous latest-value snapshots sampled about every 10 ms, not matched samples or a complete high-frequency recording. The state and command receipt timestamps, trace timestamp, and service request/response timestamps use the same Linux host's monotonic clock; service responses bound, but do not identify, the exact transition instant. DDS observation and an estimated torque do not prove ownership or physical execution. Confirm the node, monitor and trace are from the reviewed versions before interpreting records.

`peak_dq` is the monitor's cumulative maximum, not an instantaneous phase peak. The runner records the highest cumulative value and the phase and time when it first observes a value above 2 rad/s. An excess or observation failure triggers an immediate revocation attempt; any observed excess or incomplete observation changes the final result to `needs_operator_check`. After revocation the runner observes telemetry for a bounded 0.5-second window without sending motor commands, then takes a fresh final sample before stopping the monitor. The observation ends at that sample; it cannot establish behavior afterward or guarantee safe mechanical recovery. Original preparation result and revocation evidence remain separate in the summary.

Run offline checks with `python3 tools/h1_2_policy_hardware/test_acceptance_offline.py`.

`get_fsm_readonly.cpp` is a separate read-only H1 loco GET_FSM_ID diagnostic. It sends one query on eth0/domain 0 with a 3-second RPC timeout, prints the return code and raw response before attempting to parse a successful response, and never publishes LowCmd or calls a mode-changing API. A successful query does not establish debug mode or exclusive control. Build it with the same command above, replacing `prepare_monitor.cpp` with `get_fsm_readonly.cpp` and the output path with an independent temporary filename. Building does not run the probe; review before any execution.

The runner accepts `--joint-command-mode torque|position_pd` (default `torque`) and records it in the summary. Before authorization it requires the node status to report the selected mode and matching software-clamp status; an older or mismatched node is rejected. Native position PD is not constrained by the bridge software torque clamp; firmware torque limits and prior successful gains are not established. Existing authorization and zero-budget gates remain in effect.

For hardware `position_pd`, the runner requires the sample torque projection and `hold_supported_release_v3` protocol before authorization; v2 and older nodes are rejected. Execution requires an interactive terminal before authorization. The projection evaluates ideal PD torque from fresh sampled state; `limited_frames` counts successful projection calculations that changed at least one joint target; it increments only after a successful write. It does not establish firmware torque limits, physical execution, or safety. Software torque clipping remains disabled for native PD. V3 was deployed on 2026-11-05 and passed output-disabled board validation; it has not been verified in a real-robot action. Earlier v2 deployment records remain historical.

FixStand and ArmHoldStand use a three-second entry blend from the first emitted frame; the runner checks the entry transition has completed before continuing. Position and gain blending changes the intermediate preparation trajectory, while retaining its three-second endpoint. A normal Passive request or exhausted policy budget enters `Hold`, retaining the last successfully written command without automatic release. Hold may already have kp=0 and provide damping only; it does not guarantee positional or mechanical support. After externally supporting the robot and both arms, the operator types exactly `RELEASE`; only then does the runner request `release_supported`.

The local v3 exit protocol blocks release at the 0.5 rad/s motion threshold. It first transitions for 3 seconds toward each joint's damping endpoint `max(from, passive)` while reducing kp. It then reads the latest dq for all 27 joints at each control tick; every sample must be strictly below 0.1 rad/s continuously for 0.5 seconds before the 3-second kd reduction begins. Any non-quiet sample during the kd phase freezes the transition and recomputes the remaining reduction. The overall 10-second deadline latches the blocked state. Status reports `release_blocked`, `release_phase` and `release_kp_zero`; output transition values are `exit`, `hold` or `none`. The runner reads the latest state at 50 Hz, so it cannot guarantee that no instantaneous 0.5 rad/s spike happens between reads or control ticks. A blocked exit remains in Hold and is not retried. Hold may already have kp=0 and provide damping only; position or mechanical support is not guaranteed. The runner reports `needs_operator_check`, continues monitoring, and waits for the operator to explicitly confirm physical safety handoff by typing `REVOKE` before it calls `revoke_output`. Faults in controller state, monitor, telemetry/CRC, authorization, or the independent cumulative 2 rad/s speed protection still immediately attempt revocation. The runner allows up to 12 seconds for a normal exit; timeout also enters the existing revoke/check path. EOF, interruption, excess speed, or observation failure requires an operator check. All thresholds and transitions are engineering conditions, not safety guarantees; gains, blending and telemetry do not prove safe motion or mechanical support.

The policy budget counts policy frames actually written; `--policy-steps` accepts 0–155. Values above 5 require `position_pd` and `--max-policy-seconds` in the range 0–3.1 seconds; the seconds value is a monotonic execution deadline. In particular, one frame does not complete the three-second entry blend or demonstrate that the policy meaningfully influenced motion.

Even with the extended frame and time limits, the policy budget does not establish a complete ONNX control handover. Do not treat a larger budget as a substitute for the remaining validation.

The runner and `process_guard.py` must be installed together. On Linux, both owned processes request SIGTERM if the runner dies; a failed guard prevents the child program from starting. A forced runner death cannot run normal cleanup or establish safe mechanical behavior.

### 隔离的人工短速度试验

`run_acceptance.py --continuous-walk-trial` 要求 `position_pd`、零策略步数和时限、`--confirm-supported-upright`；实际执行还要求交互终端及既有调试/独占控制确认。试验使用独立命名空间中的人工速度与心跳话题，不向生产导航话题发布。现场 `CONFIRM` 后进入 ArmHold，等待就绪和连续 3 秒稳定（任一关节速度达到 0.5 rad/s 重置计时，最多等待 10 秒），再发送一次 `vx=0.12 m/s` 的 0.5 秒单调时钟窗口，随后持续零指令并监测 ArmHold；机器人及双臂获得外部支撑后输入 `REVOKE` 撤权。异常按原保护撤权，不自动释放或降增益。

心跳和速度由 20 ms 定时器发送，依赖新鲜遥测和主循环最长 0.15 秒的状态授权租约；状态服务阻塞时租约到期即停止发布。桥接门控超时 0.2 秒、速度超时 0.4 秒是后备保护，Python 时间窗口不保证物理上在 0.5 秒停步。`summary.json` 分别记录桥接状态中是否观察到非零 `policy_cmd` 和归零后 ArmHold 的零 `policy_cmd`；两者均不能证明实际迈步，须由现场观察。该入口的软件测试不等于实机验证。

人工试验现支持固定 `--manual-motion forward|turn_left`：默认 forward 为 `(0.12,0,0)`，turn_left 为 `(0,0,0.1)`，单次窗口由 `--manual-pulse-seconds` 指定0.5–3.0秒；租约、保护和受支撑交接仍适用。2026-11-07左转软件窗口观察非零及归零，用户确认已左转并归零站稳，仅此单次参数有现场证据，见 [转向计划](../../docs/h1_2-onnx-turn-test/plan.md)。

### Persistent policy owner (local implementation, not installed)

`policy_owner.py` supervises the policy node, coordinator, and monitor independently of navigation clients. It does not authorize motor output or restart failed children. On stop or startup failure, it queries `/h1_2/policy/runtime_identity`; it only terminates the owned process group after a valid status confirms `authorized=false`, no writer, and a zero 16-byte LowCmd writer GUID. An unavailable or active status keeps the owner and children alive. The systemd template uses an infinite stop timeout so systemd cannot force-kill an active policy after a short grace period. This local implementation has not been installed or validated with a live policy node; hardware handover remains a separate operator action.
